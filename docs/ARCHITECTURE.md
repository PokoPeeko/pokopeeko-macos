# PokoPeeko — Architecture

## 1. 시스템 구성

PokoPeeko는 macOS 클라이언트와 백엔드 서버로 구성된다.

- macOS 클라이언트: 앱 활동 감지, 서버 통신, 친구 활동 상태 및 사용 시간 표시
- 백엔드 서버: 사용자 및 활동 상태 관리, 누적 사용 시간 관리, 실시간 이벤트 전달
- Firebase Authentication: Apple 로그인 인증 처리

일반적인 데이터 요청에는 REST API를, 실시간 활동 공유에는 Socket.IO를 사용한다. 일반 WebSocket 클라이언트와 직접 호환되지 않으며 공식 Swift 클라이언트를 사용한다.

## 2. 클라이언트 아키텍처

MVVM과 Feature-based 구조를 사용한다.

주요 기능은 다음과 같이 구분한다.

- Auth: 로그인 및 인증
- Main: 메인 앱 내비게이션
- MenuBar: 메뉴바 팝오버 UI
- Presence: 실시간 활동 상태 및 동기화
- Dashboard / Friends / Apps / Profile / Settings / Info / Feedback: 메인 앱의 개별 기능

기능별 내부 구조는 구현에 따라 조정할 수 있다.

### 2.1 현재 클라이언트 구성

- `MainView`는 `NavigationSplitView`로 화면을 전환하고, 섹션 없는 사이드바와 하단 피드백 버튼을 사용한다.
- `MainViewModel`은 선택 화면·친구 관리 탭과 `AppCatalog`를 보유하며 메인 앱과 팝오버에서 같은 인스턴스를 사용한다. `FriendsViewModel`을 통해 수락된 친구와 요청 목록을 공유한다.
- `Features/Apps/AppCatalog`는 `NSWorkspace` 이벤트 구독, 로컬 앱 목록, 현재 활성 앱, 차단·노출 설정을 관리한다. 여러 창에서 시작해도 구독은 한 번만 등록한다.
- `DetectedApp`은 번들 ID, 앱 이름, 앱 경로, 감지 허용·노출 여부와 직접 추가 여부를 저장한다. `UserDefaults`의 `appCatalog.v1` 키에 JSON으로 저장하며, 읽기 실패 시 기존 데이터를 덮어쓰지 않는다.
- 친구 활동 상태 UI는 `Presence`에 두고, 목록과 행을 메인 앱에서도 재사용한다.
- `Shared/Components/AppIconView`는 번들 ID로 설치된 앱을 찾아 `NSWorkspace`에서 실제 아이콘을 가져온다. 저장된 경로 또는 실행 중 앱의 정확한 이름 일치도 사용할 수 있으며, 찾지 못하면 기본 아이콘으로 표시한다. 아이콘 이미지는 메모리에 캐시하며 원격 다운로드는 하지 않는다.
- 팝오버의 화면 이동은 SwiftUI `openWindow`와 AppKit 앱 활성화·창 포커스를 함께 사용한다.
- 인증은 Apple → Firebase → 백엔드 세션 순서로 처리하고, `needsProfileSetup`으로 최초 설정과 메인 화면을 나눈다. Debug·Release 모두 단일 `Window(id: "main")`에서 로그인·프로필 설정·메인 화면을 전환하며 별도 개발용 메인 창은 제공하지 않는다.
- `FriendsViewModel`은 받은·보낸 요청 및 친구 목록을 독립적으로 읽고, 이름 검색 결과의 UUID로 요청 대상을 선택해 전송한다. 세션 변경·이전 응답·중복 조작을 방어한다.
- 프로필과 친구 기능이 공통으로 사용하는 세션 HTTP 전송·오류 디코딩은 `Shared/Networking/SessionAPIClient`에 둔다. 기존 로그인·업로드 전송은 `AuthService`에 유지한다.
- `FriendProfileViewModel`은 사용자 UUID로 프로필을 조회하고 세션 교체·늦은 응답을 방어한다. 메인 앱의 친구 행은 상세 sheet를, 메뉴바 행은 같은 창의 내부 상세를 열며 이미지 다운로드와 정적 경로 확인에는 세션을 전송하지 않는다.
- `ProfileSnapshotCache`는 조회한 프로필을 사용자 계정별로 분리해 표시용으로 보존한다. `ProfileImageCache`는 아바타 메모리·디스크 저장과 동일 이미지의 중복 요청을 관리한다. 새로고침 중 기존 프로필을 유지하며 인증 여부는 기존 세션 검사로 판단한다.
- 테마 선택은 `AppStorage`로 저장하고 `NSApplication.appearance`로 앱 전체에 적용한다. 시스템 모드에서는 nil로 복원해 창·팝오버가 macOS appearance를 상속한다. SwiftUI의 창별 `preferredColorScheme` 강제 설정을 사용하지 않는다.
- `LaunchAtLoginController`는 `SMAppService.mainApp`의 등록·해제와 실제 승인 상태를 관리한다. 앱 활성화·설정 진입 시 상태를 다시 읽으며 UI 토글만 저장해서 등록 성공으로 간주하지 않는다. 사용자 조작 없이 자동 등록하지 않는다.
- 활동 공유와 메뉴바 오프라인 포함 설정은 로컬에 저장한다. 공유를 끄면 이전 앱 이름을 비공개 상태로 교체하고, 앱 전환·heartbeat 중에도 비공개를 유지한다.
- `MusicViewModel`은 선택한 Mac 음악 앱의 로컬 감지를 유지하고 `MainViewModel`을 통해 Presence에 변경을 전달한다. Apple Events 읽기는 UI와 분리하며 기본 비활성·별도 사용자 버튼에서만 수행하는 자동화 권한 요청·연결 상태·늦은 응답을 처리한다. 로컬 재생 위치/길이는 표시 전용이며 공유 콜백의 변경 판단에서 제외한다. 표지는 곡 전환 시 한 번 읽는다. 곡·가수와 재생/일시정지 상태를 DTO로 전송하고 종료 시 음악만 삭제한다. [음악 API](API_MUSIC.md)를 따른다. 사용 시간 측정은 아직 연결하지 않았다.

### 2.2 실시간 상태 공유 구현

- `PresenceService`는 Socket.IO 연결·인증·재연결·20초 heartbeat·상태 송수신을 담당한다.
- `PresenceStore`는 UUID별 앱·음악 상태, timestamp 순서 검사, 수신 시각 기준 만료와 친구 목록 합성을 담당한다. 온라인 표시는 공유 상태의 존재를 기준으로 하며 서버 전체 접속 명단과는 구분한다.
- `MainViewModel`은 앱 감지 변경을 서비스에 직접 전달하고 친구 조회 후 상태를 재조회한다. 연결 종료·세션 교체 시 캐시를 정리한다.
- 이벤트와 배포 전제는 [실시간 API](API_PRESENCE.md)를 참고한다. 설계 목표의 서버 누적 사용 시간·앱 식별자 전송은 아직 구현하지 않았다.

## 3. 앱 활동 추적

### 3.1 현재 로컬 감지 동작

- 시작 시 현재 실행 중인 일반 앱(`activationPolicy == .regular`)을 등록한다. 백그라운드 보조 프로세스와 PokoPeeko 자신은 제외한다.
- 앱 실행·활성화·종료 알림을 구독하며 앱 전환 시 현재 활성 앱을 갱신한다. 잠자기 시 활성 상태를 비우고 깨어나면 실행 중인 앱을 다시 확인한다.
- 재감지 시 기존 차단·노출 설정을 보존한다. 차단된 앱은 일반 목록에 재등록하지 않는다.
- 삭제는 일반 목록 항목만 지우며, 다시 실행·활성화되거나 다음 실행 시 스캔되면 재등록될 수 있다. 차단 정보는 삭제와 독립적으로 보존한다.
- 직접 추가는 `.app` 파일에서 이름·번들 ID·경로를 읽거나 이름·번들 ID를 입력받는다. 이 동작은 앱을 실행하지 않는다.
- 노출을 끈 앱은 관리 목록에 유지되지만 대시보드의 활동 목록·활성 앱 표시에서 제외한다.
- 사용 시간은 계산하지 않는다. 감지·노출이 허용된 현재 앱 이름은 로그인한 동안 Socket.IO로 공유하며, 차단·비노출 앱은 비공개 표시로 대체한다.

### 3.2 서버 연동 후 이벤트 감지 및 전송

1. 클라이언트가 macOS 앱의 포커스 변경 및 종료 이벤트를 감지한다.
2. 새로 포커스된 앱의 식별 정보를 서버에 전달한다. 일반 앱 전환에서는 이전 앱의 포커스 해제 이벤트를 따로 보내지 않는다.
3. 서버가 수신 시각을 기준으로 이전 앱의 사용 시간을 확정하고 새 앱 측정을 시작한다. 앱 종료 및 포커스된 앱이 없는 상태는 별도로 처리한다.
4. 서버가 변경된 상태를 친구들의 클라이언트에 전달한다.

### 3.3 서버 연동 후 사용 시간 관리

- Xcode 같은 감지 대상 앱의 실행부터 종료까지를 한 기록 단위로 삼는다. 포커스된 시간만 누적하며 다른 앱으로 전환하면 정지한다. 대상 앱을 종료하면 해당 기록을 마감하고 다시 실행하면 새 기록을 0부터 시작한다. 날짜가 바뀌어도 초기화하지 않는다.
- PokoPeeko 실행 전에 이미 켜져 있던 앱은 감지를 시작한 시점부터 측정한다. OS의 앱 실행 시각을 얻더라도 과거 포커스 시간을 소급해서 계산하지 않는다.
- 서버는 앱별로 확정된 누적 사용 시간과 마지막으로 해당 앱에 포커스가 돌아온 시각을 관리한다. 여기서 시작 시각은 프로세스 실행 시각이 아니라 현재 이어지고 있는 포커스의 시작 시각이다.
- 클라이언트는 서버에서 전달받은 정보를 기준으로 표시 시간을 계산한다.
- 앱 전환 시 기존 앱의 누적 시간을 확정하고 새로운 활성 앱의 측정을 시작한다.
- 이전 앱이 다시 활성화되면 기존 누적 시간부터 이어서 측정한다.
- 서버와 클라이언트는 각각 시간 차이를 계산하지만, 클라이언트가 계산한 누적 시간을 서버에 매번 전송하지 않는다.
- 서버는 매초 카운터를 증가시키지 않는다. 포커스 전환·종료 같은 이벤트 때 누적을 확정하고 현재 상태를 요청받으면 저장된 누적 시간과 마지막 포커스 시각으로 계산한다.
- 늦은 접속·재접속도 일반 갱신과 같은 기준 상태를 받아 표시한다. 클라이언트의 시간 저장은 표시용 캐시이며 서버 상태를 대신하지 않는다.
- 감지 대상 앱의 실행부터 종료까지 동일한 실행 ID를 유지한다. 다른 앱으로 포커스가 이동했다 돌아오면 같은 ID를 사용해 기존 누적을 재개하고, 해당 앱을 종료한 뒤 다시 실행하면 새 ID로 새 기록을 시작한다. 앱 식별자는 어떤 앱인지, 실행 ID는 그 앱의 어느 실행인지 구분한다.
- 실행 ID는 클라이언트가 대상 앱의 실행을 식별하고 서버가 기록을 연결하는 데 사용한다. 재접속 자체를 새 앱 실행으로 간주하지 않는다. 브라우저 내부 탭 변경으로도 실행 ID를 바꾸지 않는다. 로컬 실행 매핑의 보관·복원 방식은 후속 구현 설계에서 정한다.
- 위 실행 ID와 시간 관리 방식은 확정된 동작 설계다. 실제 송수신 필드 구성·필드명·이벤트명·단위 및 친구에게 실행 ID를 전달할지는 별도로 검토하고, 백엔드 명세 확인 후 연결한다.

## 4. 실시간 상태 동기화

### 4.1 초기 연결

1. 클라이언트가 Socket.IO의 `/user-status` namespace에 세션 payload로 연결한다.
2. 서버가 저장된 친구 앱·음악 상태를 개별 이벤트로 전달한다. 현재 소켓 계약은 누적 사용 시간을 제공하지 않는다.
3. 클라이언트가 초기 상태를 반영한다.
4. 이후 변경 이벤트를 실시간으로 수신하여 상태를 갱신한다.

### 4.2 재연결

- 연결 복구 시 서버의 최신 상태를 다시 동기화한다.
- 연결이 끊긴 동안 발생한 모든 이벤트를 재생하는 대신 서버에 저장된 현재 상태와 누적 시간을 사용한다.
- 초기 상태와 실시간 이벤트의 적용 순서가 충돌하지 않도록 처리한다.

## 5. 인증 및 세션

- Apple 인증 결과를 Firebase Authentication에 전달한다.
- Firebase ID Token을 백엔드에 전달하여 사용자를 인증한다.
- 백엔드가 발급한 세션과 프로필 설정 진행 상태는 macOS Keychain에 함께 저장한다. 저장이 실패하면 인증 완료로 전환하지 않는다.
- 신규 사용자 여부는 백엔드 응답을 기준으로 판단한다.
- 내부의 프로필 설정 필요 상태가 true이면 닉네임 설정을 거치며 사진은 선택할 수 있다. 현재 서버 플래그는 사용자 요청의 임시 반전 진단 중이며, 상세 기준은 인증 API 문서를 따른다.
- 프로필 이미지는 PNG로 정규화하여 multipart의 `profile_image` 파일 파트로 업로드한다. 응답 DTO와 내부 `UserProfile` 모델을 구분한다.
- 설정 전 재실행 시 Keychain에 저장한 진행 상태로 설정 화면을 복원한다. 세션 문자열만 저장했던 이전 형식은 재로그인을 요구한다.
- 앱 시작 시 내 프로필 GET으로 세션을 검증한 후 화면을 복원한다. 인증 실패와 통신 실패를 구분하고, 새 세션으로 바뀐 뒤 이전 요청이 데이터를 적용하지 못하게 한다. 상세 내용은 [인증](API_AUTH.md), [프로필](API_PROFILE.md), [친구 요청](API_FRIENDS.md) API 문서를 참고한다.

## 6. 미확정 사항

시간 공유·음악의 정상 흐름을 우선 구현한다. 다음 후속 안정성·예외 처리 항목은 [별도 문서](FOLLOW_UP_STABILITY.md)에서 관리하며, 핵심 API에 필요한 필드와 동작은 서버 명세 확인 후 연결한다.

- Socket.IO 외부 배포 주소 및 서버 누적 시간·번들 ID 확장
- 이벤트 순서 보장 및 중복 처리
- 서버와 클라이언트의 시간 차이 처리
- 네트워크 연결 끊김 및 재연결 정책
- 앱 종료 이벤트 누락 시 처리
- 활동 데이터 저장 범위 및 보존 기간

확정된 설계는 구현과 함께 문서에 반영한다.

친구 삭제는 `FriendsViewModel`에서 UUID 기준으로 처리하고 프로필 상세 sheet에서 확인 후 실행한다. 개발용 로컬 모드의 상태·진입 경로·안내를 제거하여 메인 화면 진입은 인증 상태로만 결정한다.

메뉴바 내부 친구 상세는 `PresenceView`의 선택 상태와 `FriendPresenceRow/List`의 선택 콜백으로 표시한다. `MenuBarExtra(.window)` 내부에서 별도 native sheet/alert를 열지 않고 같은 창의 overlay와 내부 확인 UI를 사용한다. `FriendProfileView`는 내부 화면일 때 닫기 콜백을, 메인 앱 sheet일 때 기존 environment dismiss를 사용한다. `NowPlayingView`는 음악 연동과 대시보드에서 동일한 음악 모델·표지·진행률 표시를 공유하며 별도 감지나 서버 요청을 시작하지 않는다.

`UserSearchResponseDTO`는 `/api/user/search` 응답을 UserProfile로 변환한다. SessionAPIClient는 URLComponents 기반 queryItems를 지원하며 기존 본문 없는 세션 헤더 계약을 유지한다. 필터 스타일은 `Shared/Components/FilterToggle`에서 네이티브 버튼 Toggle와 진한 활성 강조색으로 통일한다.
