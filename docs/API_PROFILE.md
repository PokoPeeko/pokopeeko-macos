# 프로필 조회와 세션 확인

명세: 개발 서버 [Swagger](https://port-0-pokopeeko-mvzcjohte9c33cc4.sel3.cloudtype.app/api-docs). 두 조회 모두 `x-session-id`로 인증하고 요청 본문은 없다.

| 용도 | 메서드·경로 | 정상 응답 |
| --- | --- | --- |
| 내 프로필·세션 확인 | `GET /api/user/profile` | HTTP 200, `success`, `message`, `data` |
| UUID로 사용자 확인 | `GET /api/user/profile/{targetId}` | HTTP 200, 같은 형식 |

`data`에는 필수 UUID인 `id`, nullable 문자열 `displayName`, `profileImage`가 있다. `profileImage`는 URL이 아닌 파일명이다. 사용자 프로필 조회는 현재 백엔드 명세상 친구 관계와 무관하게 가능하다.

## 앱 동작

- 앱 시작 시 저장된 세션이 있으면 내 프로필을 조회한다. 응답 확인 전에는 메인 화면을 표시하지 않는다.
- 200 성공이면 조회한 프로필을 세션에 저장하고, 저장된 설정 필요 상태에 따라 메인 화면 또는 최초 설정 화면으로 이동한다.
- 내 프로필의 401 또는 404는 해당 저장 세션을 정리하고 로그인 화면으로 이동한다.
- 네트워크 오류·5xx·해석 불가능한 응답은 세션을 지우지 않고 재시도 화면으로 표시한다. 이 화면의 ‘다시 로그인’을 사용자가 선택한 경우에만 해당 로컬 세션과 Firebase 인증을 정리하고 Apple 로그인 화면으로 이동한다. 저장소 정리 실패나 다른 세션으로의 교체가 확인되면 오류를 표시하고 새 세션을 지우지 않는다. 서버의 로그아웃 API 호출이나 검사 우회는 하지 않는다.
- 새 로그인·프로필 설정 완료 후에는 내 프로필을 한 번 조회한다. 프로필 화면에서 수동 새로고침도 가능하다. 주기적 폴링은 하지 않는다.
- 친구 목록·메뉴바 팝오버·대시보드의 친구 행을 누르면 UUID로 사용자 프로필을 조회하는 상세 창을 표시한다. 표시 이름·이미지와 현재 수신된 활동을 보여주고 수동 새로고침을 제공한다. 세션 변경 시 창을 닫고 늦은 이전 계정 응답은 무시한다. 상세 조회 401은 요청한 세션의 만료 처리로 전달한다.
- 친구 상세는 목록의 표시 정보를 먼저 보여주고 서버에서 갱신한다. 새로고침 중에도 기존 프로필을 비우지 않으며, 일시적인 통신 실패에는 마지막 정보를 유지하고 오류를 함께 표시한다. 조회한 프로필은 현재 사용자 UUID별 메모리·디스크 캐시에 최대 256개 저장한다. 캐시는 표시용이며 인증 검사에 쓰지 않는다. 인증 실패·사용자 삭제(401·404)에는 해당 상세 정보와 캐시를 비운다. 본인 프로필 메타데이터는 기존 Keychain 세션에 저장한다.
- 이전 세션의 늦은 응답이 새 계정의 프로필을 덮어쓰거나 새 세션을 지우지 않도록 세션 ID와 요청 세대를 확인한다.
- 프로필 사진 변경은 기존 PATCH `/api/user/profile`로 PNG 파일 `profile_image`만 전송한다. `displayName` 파트는 생략한다. 선택한 사진은 저장 전 미리 보여주며 성공한 이미지 파일명과 현재 계정 UUID를 유지해 로컬 프로필을 갱신한다. 세션 일치·Keychain 저장을 확인하고, 업로드 전 시작된 프로필 조회가 새 사진을 덮어쓰지 못하게 한다. 실제 사용자 사진 업로드 검증은 사용자가 수행하며 모의 HTTP로 파일 단독 전송·401·계정 변경을 검증한다.
- 닉네임 변경은 같은 PATCH에 `displayName`만 넣고 이미지 파일 파트는 생략한다. 공백 없는 1~10자를 검증하고, 기존 값과 같으면 저장을 비활성화한다. 서버가 반환한 유효한 이름을 현재 계정의 세션에 반영하며 UUID·사진·표시 중인 사진 데이터는 보존한다. 중복 저장·401·늦은 이전 계정 응답을 방어한다.

## 이미지

사용자가 제공한 실제 주소를 HEAD 요청으로 확인해 HTTP 200 및 `image/png` 응답을 받았다. 확인된 경로는 **서버 기본 주소 + `/static/profile/` + 파일명**이다.

앱은 이 경로를 사용해 내 프로필·친구·요청 상대의 아바타를 비동기로 표시한다. 별도 인증 헤더는 이미지에 보내지 않는다. 미설정·다운로드 실패 시 기본 아바타를 사용하며 파일명이 경로를 벗어나지 않도록 검사한다. 현재 경로는 인증 없이 접근되는 정적 이미지다.

아바타는 공통 `ProfileImageCache`를 사용한다. 메모리·디스크에 있는 이미지를 먼저 표시하고 동일 URL의 동시 다운로드는 하나로 합친다. 개별 이미지 최대 8 MiB, 디스크 최대 100 MiB이며 오래된 파일부터 정리한다. 파일명이 바뀌면 새로운 URL로 내려받는다. HTTP 오류·이미지 디코딩 실패는 저장하지 않고 서버의 `Cache-Control: no-store`를 존중한다. 사용자가 직접 선택해 업로드한 본인 이미지도 반환받은 이미지 URL에 연결해 캐시한다. 이미 저장된 파일이 없고 서버가 404인 경우 캐시만으로 이미지를 복원할 수는 없다.

배포 서버에서 이전에 제공된 파일명을 다시 확인했을 때 `Cannot GET /static/profile/{fileName}` HTTP 404가 반환되었다. 이 한 파일의 실패만으로 모든 업로드 파일 누락 또는 정적 라우팅 누락 중 어느 원인인지 확정하지 않는다. 내 프로필·친구 프로필 상세의 별도 HEAD 요청·HTTP 진단·주소 확인 링크는 개발용 UI 정리로 제거했다. 정적 파일 서버·파일 존재 여부는 백엔드에서 별도로 확인해야 한다.

API용 DTO와 내부 `UserProfile`을 구분한다. 조회 DTO의 UUID는 필수다. 최초 프로필 수정 응답에는 UUID가 없으므로 로컬 `UserProfile.id`는 조회가 완료되기 전까지 nil일 수 있다.

2026-11-12 이전 공개 샘플의 배포 서버 `/static/profile/<파일명>` GET은 HTTP 404(`Cannot GET`)를 반환했다. 정적 경로 조합은 사용자와 합의한 계약을 유지하며, 파일 누락·배포 저장소·정적 서빙 설정의 실제 원인은 서버 확인이 필요하다. 프로필 상세의 별도 HEAD 진단 UI를 제거하여 캐시와 별개로 추가 요청하지 않는다. 실제 아바타는 기존 GET·이미지 디코딩·캐시를 그대로 사용한다.

프로필 화면의 사진 클릭은 기존 사진 변경 sheet를 열고, 닉네임은 기존 PATCH 요청을 인라인 편집에서 재사용한다. 조회한 이름 갱신은 저장하지 않은 편집값을 지우지 않으며 저장 후 기준값을 갱신해 재전송 버튼을 비활성화한다. 프로필 조회는 화살표 아이콘 버튼으로 수동 갱신할 수 있다.

사용자의 명시적 승인 후 앱 캐시에 있는 실제 프로필 파일명으로 현재 배포 서버의 합의된 정적 경로를 GET·HEAD 확인했고, 두 요청 모두 HTTP 404 및 JSON Content-Type을 반환했다. 토큰·세션은 읽거나 전송하지 않았다. 이전 샘플뿐 아니라 이 실제 캐시 파일도 접근할 수 없다는 사실만 확인했으며, 파일 존재·정적 경로·배포 저장소 중 원인은 백엔드에서 확인해야 한다.

재배포 관련 사용자 설명 후 다시 확인한 최신 Swagger도 이미지 URL이 아닌 파일명 응답을 명시한다. 기존 캐시 파일의 GET은 여전히 404였다. 이 결과로 재배포 후 새 업로드까지 실패한다고 판단하지 않으며, 새 파일의 주소/응답은 별도 확인이 필요하다.
